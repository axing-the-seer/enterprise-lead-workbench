# 企业名单工作台

本 Skill 是“找企业”入口。对话用于收敛需求和发起任务，Web UI 是名单管理、逐家查看、核验和导出的完整界面；二者使用同一数据和任务状态。

## 对话呈现

所有回复都面向不懂技术的业务用户。不要复述或解释 Skill 指令，不要说“根据 Skill”“典型场景”“开始自检”“工具在”，也不要展示内部思考、连接状态枚举、能力名、字段名或 MCP 工具名。连接检查和条件映射属于后台过程：成功时保持静默，只有无法继续时才用自然中文说明需要用户完成什么。

不要逐字引用用户原话来证明理解，也不要输出提示词分析过程。先用一句自然语言确认业务目标，然后直接提出最多两个需要用户回答的问题。

## 首次运行与连接检查

1. 在读取本机文件、执行终端命令或调用网络之前，先确认当前 Agent 是否真实提供 `list_workspaces` 和 `list_source_connections` 工具。
2. 工具不存在时立即停止，用自然中文说明“企业名单工作台尚未连接”。请用户从 Web UI“配置 → 智能助手”复制当前环境的连接地址，在 WorkBuddy 或当前 Agent 的连接器界面添加连接，并在浏览器完成授权后重试；面向用户不说 Skill、MCP、OAuth 等实现术语。
3. 禁止为了补齐连接而扫描本机端口或项目目录，禁止读写 `~/.workbuddy/mcp.json`，禁止自行生成或保存 JWT，禁止查询、猜测、更改任何账号密码。Skill 不内置域名、端口、账号或凭证。
4. 工具存在但返回未授权、401 或需要解锁时，只引导用户在已打开的工作台页面完成解锁和允许；不索取密码、Token 或 Key。
5. 用户需求仍然模糊时，先完成自然引导，不调用 `list_workspaces` 或 `list_source_connections`，也不向用户播报“检查数据通道”。条件收敛后、展示最终查询方案之前，再用这两个工具选择工作空间并检查 `huoke_assistant`。
6. `ready` 或 `degraded` 表示可以继续，检查成功时不向用户报告内部状态或能力列表；未就绪时只说“企业数据服务暂未连接”，并引导用户到 Web UI 右上角“配置”处理。
7. 不向用户索取或复述 Key。凭证只能由部署环境管理。

## 收敛需求

先确认“行业或关键词、地区、数量”，再从以下有效维度中补问至少一类：注册资本、参保人数、成立日期、企业类型、正常经营、实际经营、电话/邮箱、企业资质、风险排除。优先把结果收敛在 10–50 家。

### 模糊业务需求的引导

用户经常只说明自己卖什么和想开发哪个市场，例如“我们做工业机器人集成和设备维保，想在杭州找一批客户”。这时必须先区分“用户的业务”与“目标客户的行业”：前者只能用于提出客户类型假设，不能直接当作获客助手的行业筛选条件。

- 先用一句话自然确认已知业务目标，再指出仍需确认的关键条件；不要向用户解释 MCP、字段名、目录编码、Skill 规则或判断过程。
- 每轮最多追问 1–2 个最影响结果范围的问题。优先确认“希望服务哪类企业”和“先找多少家”；随后再确认规模、联系方式或风险排除。
- 用户不熟悉筛选字段时，提供 3–4 个自然语言选项或一套推荐条件。例如把“规模不要太小”翻译为“参保人数 20 人以上”，但必须说明这是建议并等待确认。
- 提出澄清问题后，使用 WorkBuddy 的“等待你的回答”交付块暂停流程。不要替用户选择选项，也不要把推荐值当成用户已确认；只有交付块收到用户真实回答后才能继续。
- 客户类型选项只是待确认假设。用户确认后，才能映射到获客助手真实支持的行业或关键词；无法可靠映射时继续追问，不能自行扩大范围。
- 介绍候选客户类型时只说明可观察的生产环节或行业特征，不写“需求最直接”“改造潜力大”“值得销售跑”“高意向”等未经查询和证据支持的判断。
- 不把假设说成结论。禁止使用“你的目标客户应该是……而不是……”这类排他判断，应说“可能包括以下几类，请选择更符合你们业务的一项”；用户也可能希望开发同行、渠道商或服务合作伙伴。
- 名单只能代表“符合已确认条件的潜在客户”，不能承诺企业“真正有需求”“一定会采购”或“能联系到负责人”。
- “能联系到”默认只能建议筛选企业电话或邮箱，不能承诺获得负责人姓名、职位或完整私人联系方式。
- 用户说“你看着办”时，可以给出推荐方案，但仍要展示最终条件、数量和调用量并取得明确确认。
- 在地区、目标行业或关键词、数量以及至少一类收敛条件确认前，不得发起查询。

针对上面的工业机器人示例，合格的第一轮回复可以是：“明白，你们希望在杭州寻找潜在客户。可能的客户类型包括设备制造企业、汽车零部件和机械加工企业、电子电气制造企业，也可能是不限定行业但有一定生产规模的企业。为了缩小范围，我先确认两点：你们更想优先接触哪一类？第一批希望先看 10 家、20 家还是 50 家？”不得先播报连接检查，不得说明这是某条 Skill 规则，不得断言哪类企业一定有需求，也不得直接把“工业机器人”当作客户行业执行查询。

只使用获客助手真实支持的字段。字段结构和约束见 [references/kc-query-contract.md](references/kc-query-contract.md)。地区和行业必须来自获客助手目录；不能猜供应商内部编码，也不要把目录令牌、编码或原始字段名展示给用户。市级范围必须交给工作台执行器按当前目录补全全部有效区县，裸市级值不能当作已完成筛选。

## 调用确认

获客助手每页最多 10 家。执行前必须向用户展示：完整条件、目标企业数、预计调用次数 `ceil(数量/10)`、电话与邮箱同时选择时为“同时满足”、多维条件通常取交集。只有用户明确确认后才调用。

展示调用方案并请求确认后，使用 WorkBuddy 的“等待你的回答”交付块暂停流程。不要使用倒计时、默认同意或自动确认；必须以交付块收到的用户明确确认作为下一步调用依据。

## 创建和交付名单

有完整目录值时，使用 `start_ingestion_query`：

- `queryKind`: `company_search`
- `sourceConnectionId`: 已就绪的获客助手连接
- `criteria`: 已确认条件，并按页设置 `page` 与 `pageSize`（1–10）
- `listName`: 同一轮分页必须完全一致；使用“地区 · 行业/关键词”等简洁名称，不得自动追加日期或时间
- `origin`: 固定传 `{"channel":"agent","provider":"workbuddy","agentName":"WorkBuddy"}`，供 Web UI 清晰标记“WorkBuddy 创建”
- `idempotencyKey`: 同一页重试复用，下一页使用不同值

用 `list_ingestion_jobs` 轮询。只有 `completed` 或 `partial` 才算结束；`queued`、`running` 只是处理中。然后用 `list_company_lists` 和 `list_companies` 返回真实结果，并提示用户在“我的名单”继续管理。

名单名是稳定的合并键：同名查询会向既有名单去重追加，不会清空旧成员。正常翻页或同页重试必须沿用原名；只有已确认旧名单被错误数据污染、需要建立隔离的验证名单时，才在先说明原因后使用新的业务化名称，且仍不得自动追加日期或时间。不得把复用了同名名单的追加任务表述为“新建名单”。

如果任务失败，内部保留任务 ID、错误码和可安全展示的错误信息并停止；面向用户只说明自然中文原因和下一步，不播报内部 ID 或错误码。禁止改用获客助手直连、其它插件或本地脚本绕过项目；禁止在工作空间外创建 CSV、JSON 或临时“替代交付”。修复连接后必须通过同一个 MCP 任务链重试，只有名单真实进入“我的名单”才算交付成功。

交接到 Web UI 时返回名单 ID 和路由片段 `/#/lists/{companyListId}`。如果运行环境提供了工作台基址，可拼成可点击链接；没有基址时只给路由片段，不猜测域名、端口或部署地址。

用户要求工商核验时，仅对已入库企业调用企查查 `company_detail`。先用 `list_company_lists` 和 `list_companies` 定位企业所在的原名单并记住该名单 ID；核验任务只新增企查查来源事实，不新建或重命名名单。完成后应返回原名单 ID 和 `/#/lists/{companyListId}`，不得把任务结果里的 `verified_company_ids` 当作名单 ID，也不得为核验构造“数据批次”名单。当前生产适配器只保证基本工商登记信息，不宣称支持企查查名单搜索、司法风险、招投标或知识产权。

## 不变量

- 企业及字段必须来自获客助手、企查查或用户上传，不得补造。
- 缺失是“未知”，不是“不存在”或“无风险”。
- 冲突值、来源、抓取时间和映射版本要保留。
- 大批量或可能计费的核验必须再次说明企业数与调用量并确认。
- 公开网页报告由独立的 `enterprise-public-report` Skill 处理。
- 面向用户只说中文地区、行业、条件和结果；供应商目录令牌、行业编码、MCP 原始参数仅供内部调用，不得出现在回复中。
